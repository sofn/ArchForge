# Contributing

ArchForge is four sibling repositories cloned side by side (no submodules): **ArchForge** (backend + contract),
**ArchForgeAdmin**, **ArchForgeWeb** and **ArchForgeDocs**. `ArchForge/repos.yaml` is the map; each repository's
`AGENTS.md` says what it may change.

## Branches and pull requests

Trunk-based, the same in all four repositories:

- `main` is always releasable. Work on a short-lived branch (`feat/…`, `fix/…`, `docs/…`) and open a pull request
  to `main`; CI runs on the pull request and again on `main`.
- Keep a branch to one change and rebase it on `main` rather than merging `main` in.
- Commit messages follow Conventional Commits — `type(scope): summary`, e.g. `fix(meta): …`. Explain *why* in
  the body. Do not add `Co-Authored-By` trailers.

## Before you open a pull request

```bash
./gradlew verify          # every gate: compile, static analysis, all tests, ArchUnit, coverage floors
```

Without Docker: `./gradlew verify -PexcludeTags=slow` (skips Testcontainers tests). Changes that affect startup
(configuration, profiles, compose files) also need a real boot: `./gradlew :archforge-server-admin:bootRun`.
Never silence a gate (see "Anti-bypass rules" in `AGENTS.md`).

## Changes that cross repositories

- The API contract is generated by ArchForge (`./gradlew generateOpenApi` → `spec/openapi.yaml`, never hand-edited).
  After a contract change: merge ArchForge first, then regenerate the client types in ArchForgeAdmin and
  ArchForgeWeb (`pnpm gen:api`) — their CI checks the types against ArchForge `main`.
- Breaking changes go into ArchForge `AGENTS.md` (Breaking Changes); structural decisions get an ADR in
  ArchForge `docs/adr/` — the only ADR series.
- User-facing behaviour changes are reflected in ArchForgeDocs (English and Chinese pages together).
